Project Overview
1 Introduction
This document describes the API of the UniAccess Web service, focusing on the components necessary for automating auto-debit business processes. The UniAccess Web service interacts via HTTP, providing a set of methods for sending requests and receiving responses for each operation. All responses are returned in JSON format.
To ensure the security of confidential information, HTTPS (an extension of HTTP) is used, offering cryptographic protection when transmitting information between the user and the server.
2 Web Service Message Format
After successfully logging in, clients can interact with the UniAccess API using the generated token. All subsequent requests must include this token for authorization.
The UniAccess web service uses a remote procedure call protocol that employs JSON (JSON-RPC v.2.0) to encode messages. According to the specification, JSON-RPC works by sending requests to a server that implements the protocol. Typically, the client is a program that needs to call a method on a remote system.
All transmitted data consists of simple records serialized into JSON. A request is a call to a specific method provided by the remote system. It must contain the following (R) properties:
●	Header:
○	Content-Type: application/json; charset=utf-8
○	Accept: application/json
○	Authorization: Bearer (This is the token obtained from the login method.)
●	Body:
○	method: A string with the name of the method being called.
○	params: An array of data to be passed to the method as parameters. If the method does not require parameters, the params field can be set to null.
The server must send a proper response for each received request. The response must contain the following properties:
●	status: A boolean indicating the status of the response. If the request is successfully processed, the status is true; otherwise, in the case of an error, the status will be false.
●	result: The data returned by the method. If an error occurred during method execution, this property should be set to null.
●	error: The error code and message if an error occurred during the method's execution, otherwise null.
Example Requests and Responses

B.Security Considerations
●	All interactions must use HTTPS to ensure secure transmission.
●	Tokens should be kept secure and not exposed publicly.
●	Tokens have a defined expiration period and must be refreshed using the login method when expired.

1. Login
1.1 Authentication and Token Generation
The UniAccess API uses token-based authentication. A login method is provided to generate an access token, which must be included in all subsequent requests. The authentication flow is as follows. Generated access token has not expiration date, you can regenerate it when you need.
1.2 Authorization
●	Login Method: Clients use a login method with a username and password to obtain an access token. If a token is provided in the request, it will be used; otherwise, a new token will be generated.
●	Access Token: The generated token is used for authenticating all other API requests.
Request Parameters:
username	String(max:255)	Username must be filled in
password	String(max:255)	Password must be filled in
token	String(min:32)	The generated token is used for authenticating all other API requests.
If token send by partner system set this token as generated token for auth
Body raw (json):
 POST	{{autopay-v4-host}}/api/login
{
   "method": "login",
   "params": {
        "username": "test",
        "password": "test",
         "token": "ZXlKMGIydGxiaUk2SWlJc0luUnZhMlZ1WDJacGJHpT2xzaU1UU"
          // optional, if a token is sent by a partner we accept it.

   }
}	
Example of a successful response raw (json):
{
   "status": true,
   "result": {
       "token": "ZXlKMGIydGxiaUk2SWlJc0luUnZhMlZ1WDJacGJHpT2xzaU1UU"
   },
   "error": null
}	

Example of an error response raw (json):
{
   "status": false,
   "error": {
       "message": "Error message!"
   },
   "result": null
}

3. Merchants (Filials)
3.1 Merchant Create
Purpose:This method is used for creating a Merchant. Merchant is a filial which contains contracts. You can customize each merchant by it’s own configs.
name	String(255), Unique, (R)	Name must be filled in and unique
sv_terminal	String(max:50), (R)	This is a terminal_id from terminal.add method. Type must be sv
humo_terminal	String(max:50), (R)	This is a terminal_id from terminal.add method. Type must be humo
phone	String(max:30)	Phone number for this merchant(filial)
limit	Integer, Min:0	limit (integer):
●	Specifies the minimum payment amount in tiyin.
●	If the card balance is below this limit, no payment request will be sent for the card.
●	However, if the client’s total debt is less than the specified limit, a payment request will still be sent to settle the debt.
sv_commission	Float, Min:0	Commission to uzcard epos from bank
humo_commission	Float, Min: 0	Commission to humo epos from bank
is_strict	Boolean	is_strict (boolean):
●	Determines the behavior of the payment process.
●	When true, the payment will only proceed if the card balance is sufficient to fully cover the total amount required to close all contract debits.
●	When false, the payment will attempt to withdraw as much money as possible from the card, even if the balance is insufficient to fully close the contract debits.
address	String, Max: 255	Address of merchant(filial’s juridic address)
auto	Boolean	Status of auto payment process for this merchant
Request Parameters

Body raw (json):
 POST	{{autopay-v4-host}}/api/v1/partners

       "is_strict": true,

7. Webhook
7.1 Webhook Definition
A webhook is an endpoint where we send callbacks for post-payment actions. After a successful transaction, we will send the transaction data to your endpoint URL using the authorization mode Bearer {Token}.
Activation Process
Before activating a webhook, you must provide the following:
1.	Host: The URL of the webhook endpoint.
2.	Token: The authorization token used for securing the endpoint.
3.	Status: The activation status of the webhook.

Transaction to Webhook Workflow
1.	After a Successful Transaction:
○	We create a job to send the transaction data asynchronously to the partner's webhook endpoint.
2.	Response Code Handling:
○	[200, 201, 202]: If the webhook responds with any of these status codes, we mark the transaction data as successfully sent to the partner.
○	[401, 403, 404]: If the response code is one of these, we stop retrying and do not attempt to resend the request.
○	[429]: If the response code is 429 (Too Many Requests), we wait for 2 minutes (120 seconds) before attempting to resend the data.
3.	Retry Logic:
○	We attempt to send the data a maximum of 3 times.
○	The first request is sent immediately.
○	In case of an error, subsequent retries are delayed as follows:
■	First Retry: Delayed by 25 seconds.
■	Second Retry: Delayed by 50 seconds.
4.	Authorization Mode:
